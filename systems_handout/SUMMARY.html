Flaky Network transport design

This submission implements a low-delay UDP transport for 160-byte, 20 ms audio-like frames. The selected visible-profile configuration is --delay_ms 70.

Architecture

harness source:47010
        | fixed: sequence + 160-byte payload
        v
      sender -- 32 coded fragments --> relay:47001 --> relay:47002 --> receiver
                                                                     |
                                                                     | fixed: sequence + payload
                                                                     v
                                                               harness player:47020

The sender and receiver use only the relay media path. Feedback is not used because a request and its response would both cross the impaired network and the forward path already consumes almost all of the byte budget.

Wire protocol

Every relay packet is exactly 10 bytes: a one-byte header and a nine-byte coded symbol. The header packs a three-bit sequence tag and a five-bit fragment index. The tag is intentionally compact: using the harness-provided T0 and DELAY_MS, the receiver maps it to the unique sequence that can still meet its deadline and discards fragments that are already useless.

Erasure coding strategy

160-byte payload + 2-byte sequence check
                  ↓
          eighteen 9-byte symbols
                  ↓
        (32,18) Vandermonde code over GF(256)
                  ↓
    32 fragments sent immediately; any 18 recover

The sender performs the coding as soon as a frame arrives, so every recovery packet has the same causal start time as the original frame. A Vandermonde generator matrix supplies 32 independently impaired fragments. Any 18 surviving fragments form an invertible matrix and recover all 162 source bytes.

Receiver behavior

receive 10-byte fragment
          ↓
map compact tag to a still-playable sequence
          ↓
collect distinct fragment indexes
          ↓
18 available? → invert GF(256) matrix → validate sequence → emit

The receiver stores fragments by sequence and index, tolerating drops, duplicates, delay, and reordering. At 18 fragments it uses Gaussian elimination over GF(256), verifies the encoded sequence check, and immediately emits the reconstructed harness frame. Frame and emission caches are bounded.

Bandwidth and trade-off

Each 160-byte source frame produces 32 packets of 10 bytes: 32 × 10 / 160 = 2.0x. There is no feedback traffic. Unlike whole-frame duplication, fragment coding turns independent packet delays into erasures and succeeds whenever any 18 fragments arrive before the frame deadline.

Known limits

A frame is unrecoverable if fewer than 18 distinct fragments arrive by its deadline; sufficiently long loss bursts or larger hidden delay spikes can cause that. The compact sequence tag is unambiguous at the selected 70 ms delay because the playable window is shorter than the tag's eight-frame cycle. The 68 ms visible runs passed but approached the 1% cap, so 70 ms is selected for hidden-profile margin.
