Flaky Network transport design

This submission implements a small UDP transport for 160-byte, 20 ms audio-like frames. The selected visible-profile configuration is --delay_ms 100.

Architecture

harness source:47010
        | fixed: sequence + 160-byte payload
        v
      sender -- DATA / PARITY packets --> relay:47001 --> relay:47002 --> receiver
                                                                     |
                                                                     | fixed: sequence + payload
                                                                     v
                                                               harness player:47020

The sender and receiver use only the relay media path. Feedback packet types are reserved by the protocol but are not used in this version.

Wire protocol

Media packets contain a 5-byte header followed by a 160-byte payload. The first byte packs a protocol version, packet type, FEC scheme, and group-size code; the next four bytes are a big-endian sequence number or FEC group start. DATA carries an original payload and PARITY carries XOR parity. The compact header keeps the initial format extensible while keeping bandwidth low.

Forward error correction

DATA(0) = frame 0
DATA(1) = frame 1
PARITY(0) = frame 0 XOR frame 1

DATA(2) = frame 2
DATA(3) = frame 3
PARITY(2) = frame 2 XOR frame 3

Each DATA packet is sent immediately. After the sender receives the odd frame of a pair, it computes and transmits the parity packet. If the receiver has parity and exactly one data member, it XORs the known member with parity to recover the missing original payload.

Receiver behavior

receive → validate → store DATA/PARITY by pair
                         ↓
                 recover if one member is missing
                         ↓
              forward each available frame once
                         ↓
                 remove completed pair state

The receiver does not enforce in-order output. The harness scores each sequence separately against its own deadline, so immediate forwarding avoids needless waiting. The receiver accepts parity before data, data before parity, and duplicates. Its recovery and emitted-frame caches are bounded.

Bandwidth and trade-off

For two 160-byte source frames, the sender transmits three 165-byte media packets: two DATA plus one PARITY. That is 495 / 320 = 1.546875x raw-media bandwidth, reported by the harness as 1.55x. This is below the 2.0x cap and leaves headroom, but this first design deliberately avoids feedback because retransmission adds a relay round trip.

Known limits

Pairwise XOR repairs one missing member only. Two lost data packets in one pair, or loss of a data packet together with the companion/parity needed to recover it, remains unrecoverable. Extreme jitter can also make causal parity arrive after the earlier frame's deadline.
