Flaky Network transport design

This submission implements a low-delay UDP transport for 160-byte, 20 ms audio-like frames. The selected visible-profile configuration is --delay_ms 80.

Architecture

harness source:47010
        | fixed: sequence + 160-byte payload
        v
      sender -- DATA / duplicate / XOR --> relay:47001 --> relay:47002 --> receiver
                                                                     |
                                                                     | fixed: sequence + payload
                                                                     v
                                                               harness player:47020

The sender and receiver use only the relay media path. Feedback is not used because a request and its response would both cross the impaired network and the forward path already consumes almost all of the byte budget.

Wire protocol

Every relay packet is exactly 164 bytes: a four-byte big-endian identifier and a 160-byte payload. DATA uses the original sequence number and can therefore be forwarded without repacking. An XOR packet sets the identifier's high bit; the remaining 31 bits identify the first frame of its protected pair.

Redundancy strategy

For each 20-frame block:
DATA(0)
DATA(1) + XOR(0,1)
DATA(2) + DUPLICATE(2)
...
DATA(19) + DUPLICATE(19)

Every original DATA packet is transmitted immediately. Frames 2 through 19 receive an immediate second copy, avoiding any FEC-generation delay on 90% of the stream. Frames 0 and 1 share one XOR packet, so the complete block sends 39 packets for 20 input frames while still giving every frame a recovery path.

Receiver behavior

receive → validate 164-byte packet
             ↓
       DATA? ── yes → forward once and retain pair members
             │
             no
             ↓
       store XOR → recover when exactly one pair member is known

The receiver does not enforce in-order output. The harness scores each sequence against its own deadline, so DATA is forwarded immediately and repeated copies are suppressed. XOR and DATA may arrive in either order, and pair/emission state is bounded.

Bandwidth and trade-off

For 20 source frames, the sender transmits 39 packets of 164 bytes: 39 × 164 / (20 × 160) = 1.99875x. Skipping redundancy on the first frame before adding the block's XOR also ensures that every partial-stream prefix remains at or below 2.0x. This spends the available bandwidth on proactive, low-latency recovery.

Known limits

Adjacent duplicate packets can both be lost during a burst. The first frame in each XOR pair still has a 20 ms causal recovery penalty because its parity cannot exist until the second frame arrives. Network delay extending past the selected 80 ms deadline will also defeat immediate copies, as demonstrated by the invalid 75 ms profile B experiment.
